SSL 인증서 자동 갱신은 오래전에 끝난 숙제처럼 취급됩니다. 서버를 처음 세팅할 때 certbot을 설치하고, 타이머가 돌고 있는 걸 한 번 확인하고 나면 그 뒤로는 아무도 들여다보지 않습니다. 실제로 그렇게 몇 년을 아무 문제 없이 지나가는 경우도 많습니다. 그런데 "몇 년 동안 문제가 없었다"는 사실이 "앞으로도 문제가 없다"는 근거가 되려면 전제가 하나 필요합니다. 인증서의 유효기간과 갱신 규칙이 그동안과 같아야 한다는 전제입니다.

그 전제가 이번에 깨집니다. Let's Encrypt는 2027년 2월 10일부터 기본 인증서 유효기간을 90일에서 64일로 줄이고, 2028년 2월 16일에는 다시 45일로 줄인다고 공지했습니다. 업계 전체로 보면 CA/Browser Forum이 공개 TLS 인증서의 최대 유효기간을 398일에서 47일까지 단계적으로 줄이는 일정을 이미 통과시켰습니다. 자동화가 제대로 되어 있다면 대부분은 아무것도 하지 않아도 됩니다. 문제는 "제대로"의 기준이 90일 시절에 맞춰져 있는 서버가 생각보다 많다는 점입니다. 이 글은 그 기준을 지금 다시 점검하는 방법을 정리한 것입니다.

## 무엇이 언제 바뀌는지, 날짜부터 정확히

먼저 공식 발표에 나온 날짜와 수치만 그대로 옮깁니다. 계산하거나 추정한 값은 섞지 않았습니다.

| 시점 | 바뀌는 내용 | 출처 |
|---|---|---|
| 2025년 6월 4일 | Let's Encrypt 만료 안내 메일 서비스 종료 | Let's Encrypt 블로그 |
| 2026년 5월 13일 | 선택형 tlsserver 프로필이 45일 인증서 발급 시작 | Let's Encrypt 블로그 |
| 2026년 10월 14일 | 스테이징 환경에서 64일 인증서 발급 시작 (테스트용) | Let's Encrypt 블로그 |
| 2027년 2월 10일 | 기본 classic 프로필이 64일 인증서로 전환, 도메인 인증 재사용 기간 30일에서 10일로 단축 | Let's Encrypt 블로그 |
| 2027년 5월 11일 | 마지막 90일 인증서가 만료될 것으로 예상되는 날 | Let's Encrypt 블로그 |
| 2028년 2월 16일 | classic 프로필이 45일 인증서로 전환, 인증 재사용 기간 7시간으로 단축 | Let's Encrypt 블로그 |
| 2026년 3월부터 2029년 3월까지 | 공개 TLS 인증서 최대 유효기간 398일에서 47일까지 단계적 단축 (모든 공인 CA 대상) | CA/Browser Forum Ballot SC-081 |

몇 가지는 짚고 넘어가야 합니다. 우선 이미 발급된 인증서를 폐기하는 변화가 아닙니다. 2027년 2월 10일 이후에 새로 발급되거나 갱신되는 인증서부터 64일이 적용됩니다. 그래서 장애가 나더라도 2월 10일 당일이 아니라, 그 뒤 첫 갱신 이후의 어느 날 조용히 터질 가능성이 큽니다. 원인과 증상 사이에 몇 주의 간격이 생긴다는 뜻이고, 이런 종류의 장애가 가장 추적하기 어렵습니다.

또 하나, Ballot SC-081은 Let's Encrypt만의 이야기가 아닙니다. 돈을 내고 사는 유료 인증서도 같은 규칙을 따릅니다. 1년짜리 인증서를 사서 1년에 한 번 담당자가 손으로 교체하던 방식은 이 일정 안에서 점점 버티기 어려워집니다. 연 1회였던 수작업이 몇 년 뒤에는 한 달 반 남짓마다 돌아오는 일이 되기 때문입니다.

반대로 걱정하지 않아도 되는 부분도 있습니다. Let's Encrypt는 유효기간이 줄어 하루 갱신 요청이 늘어나더라도 레이트 리밋은 바꾸지 않는다고 밝혔습니다. 레이트 리밋은 새 도메인 발급에 걸리는 것이고 갱신은 대상이 아니기 때문입니다. 인증서가 많은 서비스라도 갱신 횟수 때문에 한도에 걸릴 일은 없다는 뜻입니다.

## 자동 갱신이 '설치돼 있다'와 '돌고 있다'는 다른 이야기입니다

인증서 만료 장애는 대개 자동화가 아예 없어서가 아니라, 자동화가 있다고 믿었는데 어딘가 한 군데가 끊겨 있어서 생깁니다. 제가 서버 점검을 맡을 때 의심부터 하는 지점은 크게 다섯 곳입니다.

- **갱신 시점이 숫자로 박혀 있는 경우**: "만료 30일 전에 갱신"이나 "60일마다 강제 갱신" 같은 규칙이 크론, 래퍼 스크립트, 운영 문서에 고정돼 있으면 유효기간이 줄어드는 순간 계산이 어긋납니다. Let's Encrypt는 공지에서 아예 83, 80, 60 같은 숫자를 크론 작업과 래퍼 스크립트, 런북에서 grep해 보라고 권합니다.
- **갱신은 됐는데 서버가 새 인증서를 모르는 경우**: 파일은 새것으로 바뀌었는데 웹 서버를 다시 읽어 들이지 않아 옛 인증서를 계속 내보내는 상황입니다. 디스크에서는 정상, 브라우저에서는 만료로 보입니다.
- **만료 메일을 감시 수단으로 쓰던 경우**: Let's Encrypt가 보내던 만료 안내 메일은 2025년 6월에 끝났습니다. 그 메일이 사실상 유일한 경보였던 팀이라면 지금은 아무 경보도 없는 상태입니다.
- **도메인 검증 경로가 막힌 경우**: 방화벽 규칙, CDN 설정, 리다이렉트 변경 때문에 HTTP-01 검증 요청이 서버에 닿지 않으면 갱신이 실패합니다. 인증 재사용 기간이 30일에서 10일, 이어서 7시간으로 줄어들면 예전에 받아 둔 검증 결과로 넘어가던 갱신도 매번 다시 검증을 거쳐야 합니다.
- **자동화 바깥에 놓인 인증서**: 로드밸런서에 손으로 올린 인증서, 사내 관리 도구, 오래된 스테이징 서버처럼 처음부터 자동화 대상이 아니었던 것들입니다. 대체로 이쪽이 가장 먼저 만료됩니다.

다섯 가지 모두 공통점이 있습니다. 평소에는 아무 신호도 없다는 점입니다. 그래서 점검은 "문제가 생기면 알게 되겠지"가 아니라 "문제가 생기기 전에 일부러 들여다본다"는 방향이어야 합니다.

## certbot을 쓴다면 확인할 세 가지

국내 소규모 서비스에서 가장 흔한 조합은 NGINX나 Apache 앞단에 certbot을 붙인 형태일 겁니다. certbot 사용자라면 아래 세 가지만 확인해도 대부분의 위험을 걸러낼 수 있습니다.

### 1. certbot 버전과 갱신 판단 기준

certbot 공식 문서에 따르면 **certbot 4.0.0부터** 인증서는 남은 수명이 전체의 3분의 1보다 적어졌을 때 갱신 대상이 됩니다. 유효기간이 10일 이하인 짧은 인증서는 절반이 기준입니다. 4.0.0 이전에는 기준이 "만료 30일 전"으로 고정돼 있었습니다.

이 차이가 왜 중요한지 직접 계산해 보면 이렇습니다. 64일 인증서에서 남은 수명 3분의 1은 대략 21일이니, 발급 후 43일 무렵에 갱신을 시도합니다. 옛 고정 기준인 30일을 적용하면 발급 후 34일쯤 갱신하게 됩니다. 둘 다 당장 위험하지는 않지만, 비율 기반 기준은 유효기간이 바뀌어도 알아서 따라가고 고정 기준은 그렇지 않습니다. 오래된 OS 패키지로 설치한 certbot은 버전이 한참 뒤처져 있는 경우가 많으니 `certbot --version`부터 확인하는 걸 권합니다.

### 2. 타이머가 실제로 돌고 있는지

certbot 문서는 설치 방법에 따라 갱신 타이머가 미리 들어 있을 수 있으니 시스템 크론탭이나 systemd 타이머에서 `certbot renew`를 찾아보라고 안내합니다. 확인은 이 정도면 충분합니다.

```bash
# 설치 방법에 따라 둘 중 한 곳에 들어 있습니다
systemctl list-timers | grep -i certbot
grep -rn "certbot" /etc/crontab /etc/cron.d/ 2>/dev/null
```

`certbot renew`는 갱신 시점이 된 인증서만 건드리기 때문에 하루에 여러 번 돌려도 괜찮다는 것이 공식 설명입니다. 반대로 `--force-renewal`을 매일 돌리는 크론은 문서에서도 레이트 리밋에 금방 걸린다고 경고하는 방식이니, 그런 줄이 남아 있다면 지우는 편이 맞습니다.

### 3. 갱신 뒤에 서버를 다시 읽게 하는 훅

앞에서 말한 "파일은 새것, 서버는 옛것" 문제는 `--deploy-hook`으로 막습니다. 문서 설명대로 이 훅은 인증서가 실제로 새로 발급됐을 때만 실행됩니다. 갱신할 것이 없어서 넘어간 경우에는 돌지 않으므로 웹 서버를 쓸데없이 재시작하지 않습니다.

```bash
# 실제로 새 인증서가 발급됐을 때만 NGINX 설정을 다시 읽습니다
sudo certbot renew --deploy-hook "systemctl reload nginx"
```

한 번 이렇게 실행해 두면 해당 옵션이 인증서별 갱신 설정에 저장돼 다음 갱신부터 계속 적용됩니다. 참고로 `certbot renew`의 종료 코드는 갱신이 필요 없을 때도 0이라서, "종료 코드가 0이면 재시작" 같은 래퍼 스크립트로는 실제 갱신 여부를 구분할 수 없습니다. 이것도 문서에 명시된 내용입니다.

![수명의 3분의 1이 남은 지점에서 새 인증서로 넘어가는 갱신 흐름 일러스트](/images/tistory/tls-certificate-renewal-64-day-checklist/2.jpg)

<p style="font-size:13px;color:#888;text-align:center;">일러스트: 수명의 3분의 1이 남은 지점에서 새 인증서로 넘어가는 갱신 흐름</p>

점검할 때 `certbot renew --dry-run`도 함께 돌려 보게 되는데, 이 명령의 범위는 정확히 알고 쓰는 게 좋습니다. dry-run은 Let's Encrypt 스테이징 서버로 갱신 절차를 시험해 보고 인증서는 저장하지 않습니다. 그래서 "검증 경로가 살아 있는지, 설정이 깨지지 않았는지"를 확인하는 데는 좋지만, 기본값으로는 deploy 훅도 실행하지 않습니다. 훅까지 시험하려면 `--run-deploy-hooks`를 붙여야 합니다. dry-run이 통과했다고 해서 64일 전환 이후의 동작까지 보장되는 것은 아니라는 점도 기억해 둘 만합니다.

## ARI, 갱신 시점을 CA에게 맡기는 방법

유효기간 단축 공지마다 Let's Encrypt가 빠짐없이 권하는 것이 ARI(ACME Renewal Information)입니다. 2025년에 RFC 9773으로 표준이 됐고, 개념은 단순합니다. 클라이언트가 인증서 식별자로 CA에 물어보면 CA가 "이 기간 안에 갱신하라"는 권장 창을 돌려줍니다.

```json
GET /renewal-info/ACME_KEY_IDENTIFIER

{
  "suggestedWindow": {
    "start": "2026-02-03T04:00:00Z",
    "end": "2026-02-04T04:00:00Z"
  }
}
```

이 방식의 장점은 갱신 시점을 내 서버의 계산이 아니라 CA의 판단에 맡긴다는 데 있습니다. 유효기간이 64일이든 45일이든 클라이언트 코드를 고칠 필요가 없고, CA가 대규모 폐기 같은 사고를 겪으면 권장 창을 앞당겨 급히 갱신하게 만들 수도 있습니다. Let's Encrypt 블로그에 실린 Shopify 사례가 바로 이 지점을 짚습니다. 수백만 개 도메인의 인증서를 "만료 30일 전"이라는 고정 기준으로 관리하다가 ARI로 바꾸면서, 유효기간 변화와 폐기 사고에 코드 수정 없이 대응할 수 있게 됐다는 내용입니다.

Let's Encrypt의 64일 공지는 ARI를 지원하는 클라이언트로 자동 갱신을 하고 있다면 준비가 끝난 것이라고 설명합니다. 어떤 클라이언트가 ARI를 지원하는지는 각 클라이언트 문서에서 확인하라고 안내하고, certbot도 ARI를 지원하는 클라이언트로 언급됩니다. 다만 직접 ACME 라이브러리를 붙여 만든 사내 도구라면 이야기가 다릅니다. 그런 도구는 대부분 고정 기준을 쓰고 있을 테니, 이번 기회에 ARI 지원 여부부터 확인해 볼 만합니다.

## 파일을 바꾸는 것까지가 아니라 배포까지가 갱신입니다

인증서가 웹 서버 한 대에만 붙어 있다면 deploy 훅 하나로 끝납니다. 하지만 서비스가 조금만 커져도 인증서는 여러 곳에 흩어집니다. 웹 서버 여러 대, 로드밸런서, 컨테이너 이미지 안, 메일 서버, 사내 도구까지. 이럴 때 갱신이란 "새 파일이 생겼다"가 아니라 "새 인증서가 필요한 모든 곳에 배포되고, 각 서비스가 다시 읽어 들였다"까지를 뜻해야 합니다. Let's Encrypt도 64일 공지에서 이번 변화를 리로드와 배포까지 자동화하고 갱신 실패 알림을 붙일 기회로 삼으라고 권합니다.

![발급부터 서버 리로드까지 이어지는 인증서 갱신 파이프라인 일러스트](/images/tistory/tls-certificate-renewal-64-day-checklist/3.jpg)

<p style="font-size:13px;color:#888;text-align:center;">일러스트: 발급부터 서버 리로드까지 사람 손 없이 이어지는 갱신 파이프라인</p>

AWS를 쓰는 팀이라면 ACM(AWS Certificate Manager)의 관리형 갱신 범위를 정확히 알아 두는 것이 좋습니다. AWS 문서 기준으로 ACM이 발급하고 DNS 검증을 쓰는 인증서는 자동 갱신되며, ELB나 CloudFront 같은 다른 AWS 서비스에 연결된 인증서가 대상입니다. 반면 **ACM으로 가져온(import) 인증서는 관리형 갱신 대상이 아닙니다.** ACM의 ACME 인증서 자동화로 발급한 인증서도 관리형 갱신이 아니라 ACME 클라이언트가 갱신을 책임집니다. 그리고 ACM 인증서는 리전 단위 리소스라서, 같은 도메인 인증서가 여러 리전에 있으면 각각 따로 갱신됩니다.

현장에서 제가 가장 주의 깊게 보는 것은 import한 인증서입니다. 다른 곳에서 산 유료 인증서를 ACM에 올려 로드밸런서에 붙여 두면, 콘솔에서는 다른 ACM 인증서와 나란히 보여서 자동으로 관리되는 것처럼 착각하기 쉽습니다. 최대 유효기간이 계속 줄어드는 흐름에서는 이런 인증서를 ACM 발급 인증서로 바꾸거나, 최소한 만료 감시 대상 목록 맨 위에 올려 두는 편이 안전합니다.

## 만료 알림은 이제 직접 만들어야 합니다

Let's Encrypt가 만료 안내 메일을 끝낸 이유는 공지에 분명히 나와 있습니다. 자동화가 충분히 보급됐고, 발급 기록과 연결된 수백만 개의 이메일 주소를 보관하는 것이 개인정보 측면에서 부담이었고, 비용과 운영 복잡도도 무시할 수 없었다는 것입니다. 대신 Let's Encrypt는 모니터링 서비스 목록 페이지를 두고 외부 서비스를 쓰라고 안내합니다. Red Sift Certificates Lite는 인증서 250개까지 무료로 감시할 수 있다고 소개돼 있고, UptimeRobot이나 Datadog처럼 이미 쓰고 있을 법한 도구도 목록에 있습니다.

외부 서비스를 붙이기 어렵거나, 먼저 가볍게 시작하고 싶다면 OpenSSL만으로도 충분히 쓸 만한 점검을 만들 수 있습니다. 핵심은 `openssl x509 -checkend` 옵션입니다. 공식 문서 설명대로 인증서가 지정한 초 안에 만료되면 0이 아닌 종료 코드를 돌려줍니다. 아래 스크립트는 실제 서버가 내보내는 인증서를 받아서 검사하기 때문에, 디스크의 파일이 아니라 사용자가 보는 인증서를 기준으로 판단합니다. 앞에서 말한 "파일은 새것, 서버는 옛것" 문제도 여기서 같이 잡힙니다.

```bash
#!/usr/bin/env bash
# 사용법: ./check-cert.sh example.com [남은 일수 기준, 기본 21]
set -u
HOST="$1"
DAYS="${2:-21}"
SECONDS_LEFT=$((DAYS * 24 * 60 * 60))

CERT=$(echo | openssl s_client -connect "${HOST}:443" -servername "${HOST}" 2>/dev/null \
  | openssl x509 2>/dev/null)

if [ -z "$CERT" ]; then
  echo "[FAIL] ${HOST}: 인증서를 가져오지 못했습니다"
  exit 2
fi

END_DATE=$(echo "$CERT" | openssl x509 -noout -enddate | cut -d= -f2)

if echo "$CERT" | openssl x509 -noout -checkend "$SECONDS_LEFT" >/dev/null; then
  echo "[OK]   ${HOST}: 만료 ${END_DATE}"
else
  echo "[WARN] ${HOST}: ${DAYS}일 안에 만료됩니다 (${END_DATE})"
  exit 1
fi

# 사용 예
# ./check-cert.sh blog.example.com        # 기본 21일 기준
# ./check-cert.sh api.example.com 15     # 15일 기준
```

macOS의 OpenSSL로 실제로 돌려 보면 정상일 때는 만료 시각과 함께 OK가, 기준일보다 적게 남았을 때는 WARN과 종료 코드 1이, 연결 자체가 안 되면 FAIL과 종료 코드 2가 나옵니다. 크론에 등록하고 종료 코드가 0이 아닐 때 슬랙이나 메일로 보내기만 하면 작은 만료 감시기가 됩니다.

기준일을 며칠로 잡을지가 남는데, 저는 "정상이라면 이미 갱신됐어야 하는 시점"을 기준으로 잡습니다. 64일 인증서를 3분의 1 지점에서 갱신한다면 남은 기간이 21일 아래로 떨어진 인증서는 갱신에 한 번 이상 실패했다는 뜻이 됩니다. 그래서 위 스크립트의 기본값을 21일로 두었습니다. 45일 인증서로 넘어가면 같은 계산으로 15일 정도가 됩니다. 이 숫자 역시 고정값이니, 유효기간이 바뀔 때 함께 고칠 항목으로 런북에 적어 두는 것이 좋습니다.

<p style="font-size:13px;color:#888;text-align:center;">일러스트: 대시보드의 인증서 경고를 휴대폰 알림으로 받는 개발자</p>

한 가지 덧붙이면, 감시는 갱신을 담당하는 서버와 다른 곳에서 도는 것이 원칙입니다. 갱신하는 서버가 멈추면 그 서버에서 도는 감시도 같이 멈추기 때문입니다. 소규모 팀이라면 이미 운영 중인 모니터링 서버나 CI의 예약 작업에 붙이는 정도로도 충분합니다.

## 지금부터 2028년까지, 시점별로 할 일

모든 걸 한 번에 바꿀 필요는 없습니다. 64일 전환까지는 아직 석 달 가까이 남아 있고, 45일 전환은 그보다 1년 뒤입니다. 저라면 이렇게 나눠서 처리하겠습니다.

### 이번 주 안에

- 운영 중인 도메인과 인증서 목록을 만든다. 웹 서버, 로드밸런서, 메일 서버, 사내 도구까지 포함한다.
- 각 인증서가 누구에 의해, 어떤 방식으로 갱신되는지 옆 칸에 적는다. 적을 수 없는 인증서가 첫 번째 위험 요소다.
- 크론, 래퍼 스크립트, 런북에서 83, 80, 60, 30 같은 고정 일수를 grep한다.
- 외부 만료 감시를 하나 붙인다. 서비스든 위 스크립트든 상관없다.

### 2027년 2월 10일 전까지

- certbot은 4.0.0 이상으로 올리고, 사내 ACME 도구는 ARI 지원 여부를 확인한다.
- 모든 인증서에 deploy 훅이나 그에 준하는 리로드 단계를 붙인다.
- 스테이징 환경에서 64일 인증서로 갱신과 배포 흐름을 한 번 끝까지 돌려 본다. Let's Encrypt 스테이징은 2026년 10월 14일부터 64일 인증서를 발급하고 있다.
- ACM에 import한 인증서는 ACM 발급으로 바꿀 수 있는지 검토한다.

### 2028년 2월 16일 전까지

- 인증 재사용 기간이 7시간으로 줄어드는 것에 대비해, 검증 경로(HTTP-01 경로나 DNS 레코드 자동 수정 권한)가 매번 살아 있는지 확인한다.
- 감시 기준일을 45일 인증서에 맞게 다시 계산한다.
- 수작업 교체가 남아 있는 인증서가 있다면 이 시점에는 0개를 목표로 한다.

인증서 만료는 기술적으로 어려운 장애가 아닙니다. 원인을 알고 나면 허탈할 만큼 단순합니다. 그런데 바로 그 단순함 때문에 담당자가 없는 영역이 되기 쉽고, 소규모 팀일수록 더 그렇습니다. 유효기간이 줄어든다는 건 이런 공백이 드러나는 주기도 그만큼 짧아진다는 뜻입니다. 석 달이라는 시간이 남아 있을 때 목록 한 장을 만들어 두는 것, 이번 변화에 대비하는 일은 사실 거기서부터 시작입니다.
