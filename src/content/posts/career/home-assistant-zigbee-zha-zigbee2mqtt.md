USB 동글을 미니PC에 꽂고 홈어시스턴트 화면을 열면, 지그비를 붙이는 길이 두 갈래로 나뉩니다. 하나는 설정 화면에서 바로 추가하는 내장 통합 ZHA(Zigbee Home Automation)이고, 다른 하나는 Zigbee2MQTT라는 별도 프로그램을 띄운 뒤 MQTT로 홈어시스턴트와 잇는 방식입니다. 검색해 보면 양쪽 모두 "이게 정답"이라는 글이 많아서, 처음 지그비를 들이는 단계에서 여기서 한참 멈추기 쉽습니다.

예전에 쓴 [홈어시스턴트 구축기](/posts/home-assistant-smart-home-guide/) 끝에 "지그비 센서 구성과 자동화 YAML은 따로 정리하겠다"고 적어 두었는데, 이 글이 그 후속편입니다. 홈어시스턴트 지그비 연동을 처음 하는 분이 ZHA와 Zigbee2MQTT 중 무엇으로 시작할지, 동글은 어떤 기준으로 고르고 어디에 꽂을지, 센서는 어떤 순서로 붙일지, 그리고 붙인 센서로 첫 자동화를 어떻게 쓰는지까지 순서대로 다룹니다. 설정 화면 경로와 YAML 문법은 이번에 홈어시스턴트와 Zigbee2MQTT 공식 문서(2026년 11월 기준)를 열어 다시 확인한 내용만 적었습니다.

## 지그비 연동에서 실제로 고르는 것은 '몇 겹으로 운영할까'입니다

ZHA와 Zigbee2MQTT는 둘 다 같은 일을 합니다. USB 동글(코디네이터)을 통해 지그비 네트워크를 만들고, 거기에 붙은 센서와 조명을 홈어시스턴트에서 쓸 수 있게 해 줍니다. 차이는 그 사이에 몇 개의 프로그램이 끼어 있느냐입니다.

ZHA는 홈어시스턴트 안에 들어 있는 통합입니다. 공식 문서는 ZHA를 "하드웨어에 종속되지 않는 지그비 게이트웨이 구현"이라고 소개하고, 대부분의 제조사 전용 허브를 대신해 하나의 지그비 네트워크를 만든다고 설명합니다. 동글을 꽂고 홈어시스턴트를 재시작하면 자동 발견으로 뜨는 경우가 많고, 거기서 추가 버튼을 누르면 끝입니다. 구성 요소는 홈어시스턴트 하나뿐입니다.

Zigbee2MQTT는 구조가 다릅니다. Zigbee2MQTT 공식 문서의 시작 안내를 보면 필요한 것이 세 가지입니다. 지그비 어댑터, Zigbee2MQTT를 돌릴 호스트, 그리고 그 호스트에서 접근할 수 있는 MQTT 브로커입니다. 브로커는 Mosquitto를 권장한다고 적혀 있습니다. 즉 "동글 → Zigbee2MQTT → MQTT 브로커 → 홈어시스턴트"로 네 겹이 이어집니다.

저는 이 차이를 기능 비교보다 운영 비용 문제로 봅니다. 회사에서 서비스를 하나 늘릴 때마다 모니터링할 대상, 업데이트할 대상, 장애가 났을 때 의심할 대상이 하나씩 늘어난다는 걸 여러 번 겪었습니다. 집 서버도 다르지 않습니다. 브로커가 멈추면 Zigbee2MQTT가 살아 있어도 홈어시스턴트로 상태가 전달되지 않으니, 원인을 찾으려면 어느 층에서 끊겼는지부터 따져야 합니다. 반대로 층이 나뉘어 있으면 홈어시스턴트를 업데이트하거나 재시작해도 지그비 쪽은 따로 돌고 있다는 장점도 생깁니다. 어느 쪽이 낫다기보다, 몇 겹을 감당할지 먼저 정하면 선택이 쉬워집니다.

## ZHA와 Zigbee2MQTT 차이를 표로 놓고 보면

두 방식의 차이를 공식 문서에 적힌 내용 기준으로 정리하면 아래와 같습니다. 지원 기기 개수처럼 시점마다 달라지는 숫자는 일부러 넣지 않았습니다. 내 기기가 되는지는 각 프로젝트의 기기 목록에서 모델명으로 직접 찾아보는 편이 정확합니다.

| 항목 | ZHA | Zigbee2MQTT |
|---|---|---|
| 형태 | 홈어시스턴트 내장 통합 | 별도 프로그램 + MQTT 브로커 |
| 필요한 것 | 호환 코디네이터 | 코디네이터, 실행 호스트, MQTT 브로커(Mosquitto 권장) |
| 홈어시스턴트 연결 | 설정 화면에서 통합 추가 | `homeassistant: enabled: true` + 홈어시스턴트 MQTT 통합(MQTT 디스커버리) |
| 비표준 기기 대응 | ZHA Device Handlers(quirk) | zigbee-herdsman 컨버터 |
| 설정 화면 | 설정 > 연결 > Zigbee | 자체 웹 프론트엔드(기본 8080 포트) |
| 홈어시스턴트와의 관계 | 홈어시스턴트를 재시작하면 같이 재시작 | 별도 프로세스라 홈어시스턴트와 따로 돈다 |
| 애드온 설치 조건 | 해당 없음 | 64비트(aarch64·amd64)만, 라즈베리파이는 4 이상 |

표에서 눈여겨볼 줄은 두 개입니다. 하나는 비표준 기기 대응입니다. 지그비가 표준이긴 해도 제조사들이 규격을 제각각 해석하는 일이 많아서, 두 프로젝트 모두 기기별 예외 처리 코드를 따로 둡니다. ZHA 쪽은 "quirk"라고 부르는 파이썬 스크립트를 ZHA Device Handlers 프로젝트에서 관리하고, Zigbee2MQTT는 zigbee-herdsman 컨버터를 씁니다. 사기 전에 그 모델이 어느 쪽 기기 목록에 있는지 확인하는 것이 가장 확실합니다.

다른 하나는 애드온 설치 조건입니다. Zigbee2MQTT 문서는 홈어시스턴트 애드온으로 설치할 때 64비트 아키텍처만 지원하고, 라즈베리파이 3에서는 자원이 부족해 불안정할 수 있으니 최소 라즈베리파이 4를 쓰라고 경고합니다. 오래된 보드로 시작하려는 분이라면 이 조건만으로도 ZHA 쪽이 현실적인 출발점이 됩니다.

## 어느 쪽으로 시작할지 정하는 기준

표를 보고도 망설여진다면 아래 질문 순서로 좁혀 보길 권합니다.

먼저 홈어시스턴트를 어떤 방식으로 설치했는지 봅니다. HAOS로 설치했다면 두 방식 모두 쉽게 쓸 수 있습니다. 컨테이너로 설치했다면 애드온이 없으니 Zigbee2MQTT와 브로커도 직접 컨테이너로 띄워야 하고, ZHA를 쓰더라도 USB 장치를 컨테이너로 넘겨주는 설정이 필요합니다. ZHA 문서의 문제 해결 항목에도 도커에서 USB 장치에 연결이 안 되면 호스트의 장치를 컨테이너로 매핑하라는 안내가 있습니다.

다음은 MQTT를 이미 쓰고 있는지입니다. 집에 MQTT 브로커가 이미 돌고 있고 다른 기기도 MQTT로 붙여 두었다면, Zigbee2MQTT를 얹는 추가 비용은 프로그램 하나뿐입니다. 반대로 MQTT를 처음 들어 본다면, 지그비 연동을 위해 브로커 운영까지 같이 배우는 것은 출발선을 한 칸 뒤로 미는 일입니다.

마지막은 쓰려는 기기입니다. 특정 기기가 한쪽에서만 제대로 지원된다면 고민할 필요 없이 그쪽으로 갑니다.

제 기준을 하나로 줄이면 이렇습니다. 지그비가 처음이고, 운영할 서비스를 늘리고 싶지 않고, 기기도 흔한 온습도·도어·모션 센서 위주라면 ZHA로 시작합니다. 이미 MQTT를 쓰고 있거나, 지그비 쪽을 홈어시스턴트와 분리해 운영하고 싶거나, 쓰려는 기기가 Zigbee2MQTT에서만 제대로 잡힌다면 Zigbee2MQTT로 갑니다. 회사에서 도구를 고를 때도 "팀이 운영할 수 있는가"를 기능보다 먼저 보는데, 집에서는 그 팀이 저 한 사람이라 기준이 더 엄격해야 한다고 생각합니다.

한 가지 미리 알아 둘 점이 있습니다. 나중에 방식을 바꾸는 것은 생각보다 번거로울 수 있습니다. Zigbee2MQTT 문서는 어댑터를 바꿀 때 경우에 따라 모든 기기를 다시 페어링해야 할 수 있다고 적고 있습니다. 지그비 네트워크는 코디네이터를 중심으로 만들어지기 때문에, 처음 고른 조합을 오래 쓴다는 전제로 정하는 편이 마음 편합니다.

## 코디네이터(동글)는 칩과 펌웨어부터 봅니다

지그비 동글은 겉모양이 비슷해서 가격으로만 고르기 쉬운데, 공식 문서들이 공통으로 강조하는 기준은 칩과 펌웨어입니다.

ZHA 문서는 아직 코디네이터가 없다면 Home Assistant Connect ZBT-2를 권장 선택지로 안내합니다. 그리고 수동 설정 단계에서 라디오 종류를 고르게 하는데, 실리콘랩스 EmberZNet 계열(ezsp), 드레스덴 일렉트로닉 deCONZ 계열(ConBee·RaspBee), 텍사스인스트루먼트 계열(znp), ZiGate, XBee로 나뉩니다. Zigbee2MQTT 문서는 권장 어댑터를 zStack(텍사스인스트루먼트) 기반과 EmberZNet(실리콘랩스) 기반으로 꼽고, ZiGate 기반은 권장하지 않는 쪽으로 분류합니다. 오래된 CC2530·CC2531 칩은 성능이 나쁜 것으로 알려져 있다고 따로 적어 두었습니다.

그래서 동글을 고를 때는 다음 순서로 확인합니다.

- 칩이 EmberZNet 또는 zStack 계열인지 확인합니다. 두 방식 모두에서 무난하게 쓰이는 조합입니다.
- 코디네이터 펌웨어가 들어 있는지(일부 제품은 출고 시 미리 들어 있음), 펌웨어 업데이트 방법이 제조사 문서로 나와 있는지 봅니다. ZHA 문서도 문제를 더 파기 전에 코디네이터 펌웨어부터 최신으로 올리라고 권합니다.
- Zigbee2MQTT를 쓸 계획이라면 코디네이터 백업 지원 여부도 봅니다. 문서에 따르면 현재 코디네이터 백업(`coordinator_backup.json`)은 zStack과 EmberZNet 기반 어댑터만 지원합니다.
- USB나 유선 이더넷으로 연결되는 제품을 고릅니다. Zigbee2MQTT 문서는 와이파이로 연결하는 네트워크 어댑터는 직렬 프로토콜이 패킷 손실과 지연을 견디지 못해 안정성이 떨어질 수 있으니, 원격 어댑터가 꼭 필요하다면 유선 이더넷 제품을 쓰라고 권합니다.

ZHA를 수동으로 설정할 때 장치 경로는 `/dev/ttyUSB0` 같은 경로보다 `/dev/serial/by-id` 아래 경로를 쓰라고 문서가 권합니다. 장치 번호는 USB를 다시 꽂거나 재부팅할 때 바뀔 수 있지만 by-id 경로는 장치 고유 정보로 만들어지기 때문입니다. 설정 > 연결 > 시리얼(Settings > Connectivity > Serial) 화면에서 해당 포트의 정보를 열면 이 값을 복사할 수 있습니다. 서버에서 디스크를 UUID로 마운트하는 것과 같은 이유입니다.

## USB 연장 케이블이 '필수'에 가까운 이유

지그비 관련 공식 문서를 읽다 보면 가장 여러 번 반복되는 조언이 USB 연장 케이블입니다. Zigbee2MQTT의 시작 안내는 기기 연결 시간 초과, 페어링 실패, 기기가 네트워크에서 떨어지는 등 어떤 문제든 생기면 가장 먼저 할 일로 USB 연장 케이블을 꼽습니다.

이유는 간섭입니다. 지그비는 와이파이와 같은 2.4GHz 대역을 쓰는 저전력 무선이라 주변 전자기 잡음에 약합니다. ZHA 문서는 USB 3.x 포트에서 나오는 신호 잡음, 차폐가 안 된 USB 3.x 장치와 케이블을 대표적인 간섭원으로 꼽고, 지그비 어댑터를 잠재적 간섭원에서 최대한 멀리 두되 충분히 긴 차폐 USB 연장 케이블로 USB 2.0 포트에 연결하라고 권합니다. Zigbee2MQTT 문서도 동글을 컴퓨터에 바로 꽂으면 안테나가 컴퓨터의 전파와 부품에서 간섭을 받는다고 설명하고, 50cm 정도의 연장 케이블만으로도 간섭을 줄이는 데 충분하며 가능하면 차폐 케이블을 쓰라고 적고 있습니다. USB나 HDMI 포트 가까이 두면 신호가 완전히 죽을 수도 있으니 과소평가하지 말라는 경고까지 붙어 있습니다.

<p style="font-size:13px;color:#888;text-align:center;">일러스트: 컴퓨터 포트 주변의 간섭을 피해 연장 케이블로 동글을 떨어뜨려 둔 모습</p>

배치에 관해서는 이 정도를 기억해 두면 됩니다.

- 동글은 연장 케이블로 본체에서 떼고, 가능하면 USB 2.0 포트에 연결합니다.
- 와이파이 공유기, SSD, 전원 장치, 가전제품과는 거리를 둡니다.
- 가능하면 집 한가운데에 가깝게, 벽·천장·바닥에서 조금 떨어뜨려 둡니다.
- 방향을 바꿔 가며 신호 품질 값을 보면서 위치를 잡습니다. 두 문서 모두 동글을 조금 돌리는 것만으로 결과가 크게 달라질 수 있다고 설명합니다.

와이파이와 겹치는 문제가 의심될 때 채널을 바꾸는 방법도 있습니다. ZHA는 설정 > 연결 > Zigbee에서 네트워크 정보를 열어 채널을 바꿀 수 있고, "Smart"를 고르면 전체 채널을 한 번 훑어 15·20·25번을 우선해 고릅니다. 다만 한 번만 실행되는 작업이고, 모든 기기가 새 채널에 다시 붙기까지 최대 한 시간이 걸릴 수 있다고 합니다. 문서는 와이파이와 지그비 주파수가 겹칠 때는 지그비 채널보다 공유기의 와이파이 채널을 고정하는 쪽을 먼저 시도해 보라고 권합니다. Zigbee2MQTT 문서는 채널 변경 시 일부 기기를 다시 페어링해야 할 수 있다고 경고하니, 기기를 많이 붙이기 전에 정해 두는 편이 낫습니다.

## 센서 페어링 순서: 전원 기기 먼저, 배터리 센서는 나중에

지그비는 메시 네트워크입니다. ZHA 문서는 전원에 꽂혀 있는 기기 대부분이 신호를 중계하는 "지그비 라우터" 역할을 한다고 설명하고, 건강한 지그비 네트워크를 위해서는 라우터 기기가 비교적 가까이 여러 개 있어야 한다고 강조합니다. Zigbee2MQTT 문서도 거의 모든 상시 전원 기기가 라우터가 되며(중성선이 필요 없는 릴레이 상당수는 예외)고 적습니다. 반면 배터리 센서는 전력을 아끼려고 중계를 하지 않는 기기입니다.

이 구조를 알면 페어링 순서가 자연스럽게 정해집니다.

1. **동글 위치부터 고정합니다.** 연장 케이블로 위치를 잡고, 채널도 이 단계에서 정합니다. 기기를 붙인 뒤에 바꾸면 재연결을 기다리거나 다시 페어링해야 할 수 있습니다.
2. **상시 전원 라우터 기기를 먼저 붙입니다.** 스마트 플러그나 지그비 전구처럼 늘 전원이 들어가 있는 기기를 동글에서 가까운 곳부터 바깥쪽으로 하나씩 등록합니다. 그래야 먼 방까지 중계 경로가 생깁니다.
3. **배터리 센서는 설치할 자리 근처에서 페어링합니다.** 동글 옆에서 페어링한 뒤 먼 방으로 옮기면, 센서가 처음 잡은 경로가 끊어져 한동안 응답이 없을 수 있습니다. 최종 위치 근처에서 등록하면 그 자리에서 가장 가까운 라우터를 통해 붙습니다.
4. **한 번에 하나씩, 이름과 영역을 바로 정합니다.** 여러 개를 동시에 리셋하면 무엇이 무엇인지 구분하기 어렵습니다. 붙이자마자 "아이방 온습도"처럼 이름을 바꾸고 영역(방)을 지정해 두면 나중에 자동화를 쓸 때 엔티티를 찾기 쉽습니다.

ZHA에서 실제 등록 절차는 공식 문서 기준으로 이렇습니다. 설정 > 연결 > Zigbee로 들어가 오른쪽 아래의 기기 추가(Add device)를 눌러 네트워크를 엽니다. 그다음 제조사 설명서대로 기기를 공장 초기화합니다. 문서는 예시로 조명은 최대 10번까지 껐다 켜기, 스위치는 보통 리셋 버튼이나 핀을 누르는 방식을 듭니다. 몇 초 안에 기기가 나타나면 이름과 영역을 지정하고, 네트워크가 닫혔다면 다시 시도(Try again)를 눌러 다음 기기를 붙입니다.

Zigbee2MQTT는 첫 실행 때 온보딩 화면에서 어댑터를 고르고, 이후 웹 프론트엔드에서 페어링을 허용한 상태로 기기를 리셋하는 흐름입니다. 문서는 지원 기기 목록에서 내 기기를 찾아 그 페어링 방법을 따르고, 안내가 없으면 대개 공장 초기화로 페어링된다고 설명합니다. 로그에 "Successfully interviewed ... device has successfully been paired" 같은 줄이 나오면 등록이 끝난 것입니다. 홈어시스턴트에서 보이게 하려면 Zigbee2MQTT 설정의 `homeassistant: enabled: true`와 홈어시스턴트의 MQTT 통합을 켜 두어야 MQTT 디스커버리로 기기가 자동으로 들어옵니다.

## 붙인 센서로 쓰는 첫 자동화 YAML

센서를 붙였다면 이제 자동화입니다. 홈어시스턴트 자동화는 트리거(무엇이 일어나면), 조건(이럴 때만), 액션(이걸 한다) 세 부분으로 나뉩니다. 공식 문서 기준 YAML 키 이름은 `triggers`, `conditions`, `actions`이고, 트리거 종류는 `trigger: state`처럼 적습니다. 예전 글이나 오래된 예제에서 보이는 `platform:`, `service:` 표기는 지금 문서의 예시와 다르니, 복사해 쓸 때 현재 문서와 맞춰 보길 권합니다.

자동화는 UI 편집기로 만들어도 내부적으로는 YAML로 저장됩니다. 문서에 따르면 UI가 만든 자동화는 `automations.yaml`에 쓰이고 이 파일은 UI가 관리하므로 직접 고치지 말라고 안내합니다. YAML로 직접 관리하고 싶다면 `configuration.yaml`에 이름 붙은 자동화 블록을 따로 만들면 됩니다. 아래 예시의 엔티티 ID는 설명용 이름이니, 실제로는 내 센서의 엔티티 ID로 바꿔야 합니다.

![도어 센서에서 깔때기 모양 조건을 거쳐 램프가 켜지는 흐름을 그린 일러스트](/images/tistory/home-assistant-zigbee-zha-zigbee2mqtt/4.jpg)

<p style="font-size:13px;color:#888;text-align:center;">일러스트: 트리거(도어 센서) → 조건(깔때기) → 액션(조명)으로 이어지는 자동화 흐름</p>

### 예시 1: 습도가 기준 아래로 내려가면 가습기 플러그 켜기

지그비 온습도 센서와 스마트 플러그를 조합한 자동화입니다. 숫자 상태 트리거(`numeric_state`)는 값이 기준선을 "넘어가는 순간"에 한 번 반응합니다. 공식 문서도 `above: 30` 예시를 들며 30 이하에서 30 초과로 바뀔 때 실행된다고 설명합니다. 이미 40% 아래인 상태에서는 계속 반복 실행되지 않는다는 뜻이라, 켜는 자동화와 끄는 자동화를 따로 둡니다.

```yaml
automation humidity:
  - alias: "아이방 습도 낮음 - 가습기 켜기"
    id: "kids_room_humidifier_on"
    triggers:
      - trigger: numeric_state
        entity_id: sensor.kids_room_humidity
        below: 40
        for: "00:10:00"
    actions:
      - action: switch.turn_on
        target:
          entity_id: switch.kids_room_humidifier_plug

  - alias: "아이방 습도 회복 - 가습기 끄기"
    id: "kids_room_humidifier_off"
    triggers:
      - trigger: numeric_state
        entity_id: sensor.kids_room_humidity
        above: 60
    actions:
      - action: switch.turn_off
        target:
          entity_id: switch.kids_room_humidifier_plug
```

`for`는 그 상태가 일정 시간 유지돼야 실행되게 하는 옵션입니다. 센서 값이 기준선 근처에서 오르내릴 때 플러그가 켜졌다 꺼졌다 하는 것을 막아 줍니다. 다만 문서에 따르면 `for` 타이머는 홈어시스턴트가 재시작되거나 자동화를 다시 불러오면 처음부터 다시 셉니다. `id`를 넣어 두면 UI에서 이름을 바꿀 수 있고 디버그 추적(trace)도 저장된다는 점도 문서에 나와 있어서, 저는 YAML로 쓸 때 항상 넣습니다. 40%와 60%는 예시 값입니다.

### 예시 2: 밤에 현관문이 열리면 복도 조명 켜기

도어 센서는 보통 `binary_sensor`로 잡히고, 문이 열리면 상태가 `on`이 됩니다. 공식 문서의 상태 트리거 예시도 `binary_sensor.front_door`가 `on`으로 바뀔 때를 씁니다. 여기에 시간 조건을 붙여 밤에만 동작하게 만듭니다.

```yaml
automation night_door:
  - alias: "야간 현관 열림 - 복도 조명 켜기"
    id: "night_front_door_hallway_light"
    triggers:
      - trigger: state
        entity_id: binary_sensor.front_door
        to: "on"
    conditions:
      - condition: time
        after: "22:00:00"
        before: "06:00:00"
    actions:
      - action: switch.turn_on
        target:
          entity_id: switch.hallway_light
```

시간 조건에서 `before`가 `after`보다 이르면 자정을 넘기는 구간으로 처리됩니다. 문서가 바로 22시에서 6시 예시로 이 동작을 설명합니다. 구간은 `after` 시각 정각에 시작해 `before` 시각 직전에 끝납니다. 조건을 여러 개 적으면 기본적으로 모두 참이어야 액션이 실행되고, 하나만 맞아도 되게 하려면 `or` 조건으로 묶어야 합니다. 예를 들어 "가족 중 누군가 집에 있을 때만"을 더하고 싶다면 상태 조건(`condition: state`)으로 `person` 엔티티가 `home`인지 확인하는 줄을 추가하면 됩니다.

## 운영하면서 챙길 것: 업데이트와 백업

지그비 기기를 붙였다고 끝이 아닙니다. ZHA는 기기 펌웨어 OTA 업데이트 기능이 기본으로 켜져 있고, 업데이트가 있으면 홈어시스턴트의 업데이트 엔티티로 알림을 띄워 진행하거나 무시하게 해 줍니다. 다만 제조사가 펌웨어 이미지를 공개한 기기만 해당됩니다. 홈어시스턴트 자체도 매달 바뀌는 만큼, 업데이트 전에 릴리스 노트를 훑고 백업이 최신인지 확인하는 습관이 필요합니다.

회사 서버를 운영하면서 몸에 밴 원칙 중 하나는 "백업은 복구해 본 적이 있어야 백업"이라는 것입니다. 집도 마찬가지로, 홈어시스턴트 전체 백업과 별개로 코디네이터 정보가 어디에 어떻게 저장되는지 한 번은 확인해 두는 편이 좋습니다. 동글을 바꿀 때 전부 다시 페어링하느냐가 여기서 갈립니다.

## 시작 전 점검표

마지막으로 홈어시스턴트 지그비 연동을 시작하기 전에 확인할 것을 표로 정리합니다. 위에서부터 차례로 "예"가 나오면 다음 줄로 넘어가면 됩니다.

| 점검 항목 | 확인 내용 | 막히면 |
|---|---|---|
| 설치 방식 | HAOS인가, 컨테이너인가 | 컨테이너라면 USB 장치 매핑부터 준비 |
| 연동 방식 | 운영할 서비스 수를 늘려도 되는가 | 아니면 ZHA로 시작 |
| 기기 지원 | 살 기기 모델이 선택한 방식의 기기 목록에 있는가 | 없으면 다른 모델을 찾거나 방식 재검토 |
| 코디네이터 | EmberZNet 또는 zStack 계열, 펌웨어 업데이트 방법이 있는가 | CC2530·CC2531 같은 구형 칩은 피함 |
| 연결 경로 | `/dev/serial/by-id` 경로로 지정했는가 | 설정 > 연결 > 시리얼에서 복사 |
| 배치 | 차폐 연장 케이블, USB 2.0 포트, 공유기·SSD와 거리 | 방향을 바꿔 가며 신호 품질 확인 |
| 채널 | 기기 붙이기 전에 정했는가 | 와이파이 채널 고정을 먼저 시도 |
| 페어링 순서 | 상시 전원 라우터 → 배터리 센서(설치 위치 근처) | 한 번에 하나씩, 이름·영역 바로 지정 |
| 첫 자동화 | 트리거·조건·액션 하나씩, `id` 포함 | 실행 기록(trace)으로 어디서 멈췄는지 확인 |
| 백업 | 코디네이터 정보 백업 위치를 아는가 | 동글 교체 전에 문서의 이전 절차 확인 |

지그비는 붙이는 순간보다 몇 달 뒤에 "왜 이 센서만 가끔 끊기지?"를 고민하는 시간이 더 길어지는 기술입니다. 그래서 처음 고를 때 화려한 기능보다 동글 위치, 라우터 배치, 운영할 구성 요소 수처럼 지루해 보이는 것들을 먼저 정하는 쪽을 권합니다. 지난 구축기에서 다룬 서버 설치가 끝났다면, 이 글의 점검표를 위에서부터 한 줄씩 지워 나가는 것으로 다음 단계를 시작해 보세요.
